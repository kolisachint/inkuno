# Conformance data

Test data for `tests/conformance.rs` (see `docs/design/markdown_renderer.md` §11.4).

| File | Contents | Source | Version |
|--|--|--|--|
| `commonmark-0.31.2.json` | All 652 examples, unchanged | https://spec.commonmark.org/0.31.2/spec.json | CommonMark 0.31.2 (2024-01-28) |
| `gfm-0.29-extensions.json` | 24 examples of the five GFM extension sections: Tables, Task list items, Strikethrough, Autolinks (extended), Disallowed Raw HTML | `test/spec.txt` of https://github.com/github/cmark-gfm (raw file, master branch, fetched 2026-11-21) | GFM spec 0.29-gfm (2019-04-06) |
| `expected-failures.txt` | Example numbers that fail today, one `cm:N` or `gfm:N` per line | Generated by the test (`INKUNO_SPEC_WRITE=1`) | — |

Example numbers: CommonMark uses the numbers of its `spec.json`. The GFM file has no numbers in its
source, so `gfm:N` is the position of the example among all examples of `spec.txt`, in document
order (the extension examples are 198–205, 279–280, 491–492 and 621–631, 652 in that order).

Each JSON entry has `markdown`, `example`, `section`, and the `html` expected output (CommonMark
also `start_line` and `end_line`). The tests read `markdown`, `example` and `section` only.

## Updating

Replace a file only with a newer official version, then regenerate `expected-failures.txt`
(`INKUNO_SPEC_WRITE=1 cargo test -p inkuno-logic --test conformance --locked`) and review the diff:
the list may only shrink without a reason.

## Where GFM overrides CommonMark

The expected-failures list only shrinks, with one kind of exception: a CommonMark example that GFM
deliberately changes. Inkuno follows GFM there, so the CommonMark example stays listed.

| Entry | Why |
|--|--|
| `cm:612` | `foo@bar.example.com` is plain text in CommonMark; GFM's extended autolinks make it a `mailto:` link (gfm 629). |
